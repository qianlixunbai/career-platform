# 业务设计说明

本文说明 Career Platform 的目标用户、业务闭环、模块划分与关键业务规则。技术实现见 [系统架构与设计决策](ARCHITECTURE.md)，表结构见 [数据库设计](DATABASE.md)。

## 1. 目标用户与问题

目标用户是处于职业准备与实际求职阶段的高年级学生：

- 求职准备阶段主要使用职业目标、技能档案、学习计划、简历准备与岗位收集能力。
- 实际求职阶段在此基础上管理投递、测评、多轮面试、Offer 与最终复盘。

要解决的问题是：岗位信息来自企业公众号、招聘网站等多个渠道，技能、学习计划、简历版本与投递进度又分别维护在备忘录、文档和表格里，导致各环节之间没有关联，也无法回答"当时用的是哪一版简历、经历了哪些测评和面试、最终为什么结束"。

## 2. 业务闭环

```
确定求职方向
→ 学习提升
→ 准备简历
→ 收集并分析岗位
→ 投递
→ 测评 / 笔试
→ 多轮面试
→ Offer / 被拒 / 主动结束
→ 最终复盘
→ 反馈到职业方向、学习和简历
```

这个闭环允许反馈与回退：岗位要求会影响职业目标与学习计划，面试结果和最终复盘也会产生新的学习或简历调整。

## 3. 共享基础档案

个人信息、教育经历、技能、项目经历、实习经历、证书与获奖构成**共享基础档案**，作为其他所有模块的事实源，而不是一个独立的第五业务模块。

这样设计的目的是避免同一份经历在多处重复维护：简历版本从档案生成快照，岗位要求与技能档案比对，学习计划根据技能差距制定。档案后续发生变化时，**不会回写已经生成的简历快照**，因为投递时使用的必须是当时那一版内容。

## 4. 四个核心业务模块

### 4.1 职业探索与目标管理

维护职业目标、公司、岗位、原始 JD、结构化岗位要求与岗位备注，回答"准备找什么工作、市场需要什么、个人还欠缺什么"。

关键规则：

- 公司独立存在，岗位引用公司；岗位只能引用本人创建的公司。
- 岗位来源作为岗位自身的属性保存。
- 收藏或记录一个岗位不等于产生真实投递。
- 已有投递历史的岗位不能物理删除，只能归档。
- 技能类岗位要求必须关联已有的全局技能，不自动创建新技能。

### 4.2 学习提升管理

把职业目标与能力差距转换为周学习计划、任务与实际执行记录，并通过周复盘反馈到下一阶段。

关系与规则：

- 计划 1 → n 任务；任务 1 → n 学习记录；计划 1 → 0..1 周复盘。
- 学习笔记与学习资料分离，分别承载用户自己的记录和外部资料。
- 学习资料支持上传原件、解析分块与向量化，用于带来源的资料问答。
- 周复盘中的完成率、计划与实际时长等指标由 Java 计算，AI 只提供文字建议；把建议应用到表单不会自动覆盖已保存的复盘。

### 4.3 简历管理

通过简历、版本与内容条目维护面向不同岗位的求职材料，同时保留真实投递使用过的版本。

```
Resume 1 → n ResumeVersion 1 → 0..n ResumeContentItem
                              └ 0..1 ResumeFile
```

关键规则：

- `DRAFT` 版本可编辑与删除，`FINALIZED` 版本锁定且不可修改；重复定稿保持幂等。
- 历史定稿版本不随共享基础档案的后续变化而改变。
- 实际投递必须绑定本人的 `FINALIZED` 版本，草稿版本不能用于投递。
- 复制版本会生成独立的数据行，源版本与目标版本不共享可变数据。
- 含定稿版本的简历不能直接删除。

### 4.4 求职过程管理

记录一次实际投递从创建到结束的完整过程：投递、阶段历史、测评、面试、Offer 与最终复盘。

关键规则：

- 投递阶段按有限状态机向前迁移，阶段变更与历史记录在同一事务内提交。
- 同一用户与同一岗位同时只能有一条进行中的投递；已结束的历史可以保留多条。
- 测评与面试是独立的过程记录，不会隐式推进或终结投递。
- 每个投递至多一个 Offer；接受或拒绝 Offer 会驱动投递结束。
- 最终复盘只允许在投递结束后填写，且每个投递至多一份。

## 5. AI 能力与可追溯性原则

项目包含 4 个正式 AI 能力，全部嵌入既有业务流程，而不是独立于业务之外的聊天入口：

| 能力 | 输入 | 产出 |
| --- | --- | --- |
| JD 结构化解析 | 用户保存的原始 JD | 岗位要求候选、技能匹配、可回溯的证据片段 |
| 学习计划与周复盘建议 | 时间预算、职业目标、结构化岗位要求、技能与学习历史 | 可编辑的计划候选与复盘建议 |
| 岗位发现 | 职业目标与技能档案 | 候选岗位、来源链接与匹配建议 |
| 学习资料问答 | 当前计划下的学习资料 | 回答与可信来源引用 |

贯穿四个能力的原则：

1. **AI 是候选生成器，不是事实源。** 任何需要持久化的结果都必须经过用户确认。
2. **Java 负责归属、校验与写入。** 归属校验、字段与状态校验、重复校验、事务与数据库写入统一由 Java 负责。
3. **事实与建议分开建模。** 外部来源事实与模型推断的建议分别返回、展示与持久化，不把推断包装成事实。
4. **外部文本与模型输出一律视为不可信输入。** 模型不能生成可信的数据库标识，也不能直接提交事务。
5. **默认关闭且可降级。** AI、外部搜索与向量服务未配置时，传统业务链路完整可用，相关入口返回明确的不可用提示，不伪造数据。

## 6. 当前范围

已完成并包含在当前范围内的能力：

- 共享基础档案、职业探索、学习提升、简历管理、求职过程的完整后端与前端。
- 上述 4 个 AI 能力及其写入边界。
- 覆盖单元、真实数据库集成、并发、事务与 AI 契约的自动化测试。

明确不在当前范围内的能力：

- 角色权限模型、第三方登录、刷新令牌与令牌吊销。
- AI 面试与求职复盘、简历与岗位的匹配分析、通用 Agent、AI 效果评测。
- 管理员后台与企业 HR 端。
- 分布式缓存、消息队列、独立搜索引擎与多实例调度。

这些能力不是当前业务规模下的必要组件。项目优先保证已有链路的正确性、可追溯性与可解释性。
