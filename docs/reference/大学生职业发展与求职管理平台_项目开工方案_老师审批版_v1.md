## 一、项目名称

**《大学生职业发展与求职管理平台的设计与实现》**

本项目以大学生职业准备与实际求职过程为核心，不将 AI 作为系统存在的前提。AI 主要作为业务增强能力，嵌入 JD 解析、学习规划、简历分析、求职复盘、资料问答等环节。

---

## 二、项目背景与核心问题

本系统主要面向处于求职准备和求职阶段的大三、大四学生。

目前学生通常需要通过企业微信公众号、招聘网站等多个渠道搜集招聘信息，再使用备忘录记录个人想法，并通过 Excel 整理岗位和求职进度。同时，个人技能、学习计划、简历版本、投递记录、测评、面试和复盘等内容往往分散在不同工具中。

这种方式存在以下问题：

1. 岗位信息、个人资料、学习记录和求职进度分散，缺少统一管理。
2. 职业目标、技能提升、简历调整和实际求职之间缺少连续关联。
3. 同一岗位从收集、分析、投递、面试到最终结果的历史不容易完整保留。
4. 简历存在多个版本时，难以准确追溯“当时投递的是哪一版”。
5. 学习过程往往只有计划，缺少执行记录和阶段性复盘。
6. 求职结束后的经验难以沉淀，并反馈到下一轮学习与求职准备中。

因此，本项目希望把职业准备与求职过程中分散的信息和管理过程整合到一个统一平台中，帮助学生更加系统、连续地管理自己的职业发展与求职过程。

---

## 三、目标用户

本系统主要面向 **大三、大四学生**。

- **大三学生**主要处于职业准备阶段，可以通过系统逐步确定求职方向、维护个人技能、制定学习计划、准备简历，并持续收集和整理目标岗位信息。
- **大四学生**进入实际求职阶段，系统重点帮助其管理岗位投递、笔试或在线测评、多轮面试、Offer 以及求职结束后的复盘过程。

第一版以学生作为核心业务用户，不强行加入企业 HR、就业指导教师等额外角色。

---

## 四、核心业务流程

项目核心业务闭环为：

```text
确定求职方向
    ↓
积累技能与学习提升
    ↓
准备简历
    ↓
收集并分析岗位
    ↓
实际投递
    ↓
测评 / 笔试（可选）
    ↓
多轮面试
    ↓
Offer / 公司拒绝 / 主动结束
    ↓
最终复盘
    ↓
将复盘结果反馈到职业方向、学习提升和简历调整
    ↓
进入下一轮职业准备或求职
```

该流程不是完全单向的。岗位信息可以反向影响职业目标，面试和求职复盘也可以反馈到技能认知、学习计划和简历调整中。

## 五、核心业务模块

### 5.1 职业探索与目标管理

负责学生职业方向探索和求职目标管理。

主要功能包括：

- 维护职业目标；
- 管理公司信息；
- 收集并保存岗位信息；
- 保存原始 JD；
- 维护岗位要求；
- 保存个人岗位备注；
- 结合个人技能和岗位要求了解能力差距。

该模块主要回答：

> **“我准备找什么工作，市场需要什么，我与目标岗位之间还有什么差距？”**

---

### 5.2 学习提升管理

负责把职业目标和能力短板转化为实际学习过程。

基本业务结构：

```text
LearningPlan
├─ LearningTask 0..n
│  ├─ StudyRecord 0..n
│  ├─ LearningNote 0..n
│  └─ LearningMaterial 0..n
└─ WeeklyReview 0..1
```

主要功能包括：

- 创建周学习计划；
- 拆分学习任务；
- 维护任务状态；
- 记录多次实际学习执行情况；
- 编写学习笔记；
- 上传 PDF、Word 等学习资料；
- 每周完成一次学习复盘；
- 根据复盘结果调整下一阶段学习。

该模块主要回答：

> **“为了目标，我接下来应该怎么提升，我实际做了什么？”**

---

### 5.3 简历管理

负责学生求职材料的组织和版本管理。

采用：

```text
Resume
└─ ResumeVersion 0..n
   └─ ResumeContentItem 0..n
```

设计原则：

- 共享基础档案保存真实经历；
- 简历版本负责“如何选择、排序和表达这些真实事实”；
- 不同岗位可以使用不同简历版本；
- 简历版本可以从基础档案重新生成，也可以复制已有版本后调整；
- `DRAFT` 状态可编辑；
- `FINALIZED` 后锁定；
- 已定稿版本不再随着基础档案修改而变化；
- 实际投递必须绑定一个已定稿的 `ResumeVersion`。

该模块主要回答：

> **“面对不同机会，我如何准确地呈现自己，并保留当时真正投出的版本？”**

---

### 5.4 求职过程管理

负责记录一次真实求职从投递到结束的完整过程。

一条 `Application` 主要关联：

```text
Application
├─ ApplicationStageHistory 0..n
├─ Assessment 0..n
├─ Interview 0..n
├─ Offer 0..1
└─ FinalReview 0..1
```

`Application` 采用五个粗粒度阶段：

```text
已投递
→ 测评中
→ 面试中
→ Offer处理中
→ 已结束
```

部分阶段允许跳过。

终局结果包括：

- 公司拒绝；
- 学生主动结束；
- 接受 Offer；
- 拒绝 Offer。

主要业务规则：

- 收藏或记录岗位不等于创建 `Application`；
- 真正投递时才创建 `Application`；
- 同一岗位允许多次历史投递，但同一时间只允许存在一条进行中的 `Application`；
- `Application` 同时保存当前阶段和阶段变化历史；
- Assessment 和 Interview 的局部结果不自动修改 Application 的全局阶段；
- 投递时保存岗位核心快照；
- 投递必须绑定当时使用的定稿简历版本；
- 求职真正结束后才能创建最终复盘；
- 最终复盘采用“提醒但不强制立即填写”的方式；
- 已产生求职历史的岗位不物理删除，只允许归档或隐藏。

该模块主要回答：

> **“我申请了什么，现在进行到哪里，整个过程最终发生了什么？”**

---

### 5.5 共享基础档案

共享基础档案不是第五个核心业务模块，而是四个业务模块共同使用的事实数据源。

第一版至少包括：

- 个人基本信息；
- 教育经历；
- 技能；
- 项目经历；
- 实习经历；
- 证书 / 获奖经历。

其中技能采用统一设计：

```text
Skill
├─ Java
├─ Spring Boot
├─ MySQL
├─ Redis
└─ Docker

UserSkill
├─ 用户A → Java → 熟练
├─ 用户A → Spring Boot → 熟悉
└─ 用户A → Redis → 入门
```

`Skill` 作为统一技能定义，既可被 `UserSkill` 使用，也可被岗位技能要求引用。

共享基础档案的正式修改必须由用户明确确认。职业探索、学习、简历、求职复盘及 AI 可以读取或提出更新建议，但不能直接修改正式事实数据。

## 六、项目总体框架 / 系统架构

### 6.1 总体架构

```text
                         用户 / 浏览器
                              │
                         Vue 3 前端
                              │
                      REST API / SSE
                              │
                    Spring Boot 后端
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
 职业探索与目标管理      学习提升管理          简历管理
        │                     │                     │
        └────────────── 求职过程管理 ──────────────┘
                              │
                       共享基础档案
       个人信息 / 教育 / 技能 / 项目 / 实习 / 证书
                              │
          ┌───────────────────┴───────────────────┐
          │                                       │
      普通业务能力                           AI 应用能力
          │                                       │
 Controller → Service                    JD 结构化解析
          │                              学习规划与周复盘
      Repository                         面试 / 求职复盘
          │                              简历 + JD 分析
          │                              RAG / Agent
          │                                       │
          │                                  Spring AI / LLM
          │                                       │
          └───────────────────┬───────────────────┘
                              │
                           数据存储
```

### 6.2 核心架构原则

1. **四个业务模块共享同一套事实数据。**  
   个人信息、技能、项目经历等不在不同模块重复保存。

2. **删除 AI 后，系统仍然是完整业务系统。**  
   AI 是增强能力，不替代职业目标、学习、简历、投递、面试、复盘等核心业务。

3. **确定性业务交给 Java，概率性任务交给 AI。**

4. **AI 不直接修改数据库。**

统一写入边界：

```text
AI 读取业务数据
      ↓
分析 / 提出建议
      ↓
展示给用户
      ↓
用户确认
      ↓
Java Service 校验
      ↓
正式修改业务数据
```

5. **当前事实和历史记录分离。**  
   基础档案可以更新，但定稿简历、Application 岗位快照、阶段历史等历史数据不能被后续修改反向覆盖。

### 6.3 后端模块规划

```text
src/main/java/...
├── common
├── user
├── career
├── learning
├── resume
├── application
└── ai
```

业务模块内部按照典型 Spring Boot 分层组织：

```text
controller
dto
service
repository
entity
```

具体包结构将在项目审批通过、数据库模型进一步明确后最终确定。

## 七、AI 功能与可追溯性原则

本项目中的 AI 能力作为传统业务系统的增强功能存在，不替代确定性的 Java 业务逻辑。

AI 主要负责：

- 自然语言理解；
- 信息提取；
- 分析总结；
- 建议生成；
- 文档知识检索；
- Tool Calling / Agent 决策。

正式业务数据的校验、状态流转和数据库写入仍由 Spring Boot 业务代码负责。

### 7.1 AI JD 结构化解析（P0）

```text
原始 JD
   ↓
AI 结构化解析
   ↓
候选岗位要求
   ↓
用户检查 / 修改
   ↓
用户确认
   ↓
Java Service 保存
```

主要提取：

- 技能要求；
- 学历要求；
- 专业要求；
- 经验要求；
- 语言要求；
- 其他要求。

---

### 7.2 AI 学习规划与周复盘（P1）

主要输入：

- 职业目标；
- 当前技能；
- 岗位要求；
- 历史学习任务；
- 本周执行记录。

主要输出：

- 周主任务建议；
- 子任务建议；
- 时间安排建议；
- 本周完成情况总结；
- 薄弱点；
- 下一阶段建议。

AI 只生成候选方案，正式计划由用户确认后保存。

---

### 7.3 AI 面试与求职复盘（P1）

基于：

- 岗位信息；
- 实际投递简历；
- Assessment；
- Interview；
- 用户记录；
- 最终求职结果。

辅助分析：

- 表现较好的方面；
- 暴露出的知识或能力短板；
- 多轮面试中重复出现的问题；
- 后续学习建议；
- 简历调整建议；
- 下一次求职的改进方向。

---

### 7.4 简历与 JD 匹配分析（P1）

用户选择一个岗位和一个具体简历版本后，AI 进行匹配分析。

输出内容包括：

- 岗位重点；
- 当前简历覆盖情况；
- 项目经历强调建议；
- 技能排序建议；
- 表达与重点调整建议。

AI 只能提出优化建议，不能直接覆盖正式简历版本。

---

### 7.5 RAG 学习资料问答（P2）

```text
学习资料
   ↓
文档解析
   ↓
文本切分 Chunk
   ↓
Embedding
   ↓
向量检索
   ↓
RAG
   ↓
生成回答
   ↓
展示来源与原文
```

该功能重点支持 PDF、Word 等学习资料问答和来源追溯。

---

### 7.6 Agent + Tool Calling 求职学习助手（P2）

用户可以提出跨模块问题，例如：

> “结合我最近关注的岗位、当前技能和面试复盘，我下周应该重点学什么？”

Agent 根据问题选择调用相应 Java Tool 获取真实业务数据，再由模型进行综合分析。

涉及写操作时仍必须：

```text
AI / Agent 建议
→ 用户确认
→ Java Service 校验
→ 正式写入
```

---

### 7.7 AI 可追溯性原则

所有基于系统业务数据、岗位 JD、简历、面试记录和学习资料生成的 AI 分析，应尽可能展示对应依据。

涉及文档引用时，应支持查看：

- 来源文档；
- 页码或位置；
- 对应原文片段。

同时明确区分：

```text
来源事实
≠
AI 推理 / AI 建议
```

无法找到可靠依据时，不伪造引用。

## 八、P0 / P1 / P2 版本规划

### 8.1 P0：基础可交付版

目标：

> 先形成一个不依赖高级 AI 能力，也能够完整使用的大学生职业发展与求职管理系统。

主要范围：

- 共享基础档案；
- 职业目标；
- 公司、岗位、原始 JD、岗位备注；
- 岗位要求管理；
- 学习计划；
- 学习任务；
- StudyRecord；
- 学习笔记和资料；
- WeeklyReview；
- Resume / ResumeVersion；
- 简历定稿与锁定；
- Application；
- Assessment；
- 多轮 Interview；
- Offer；
- FinalReview；
- AI JD 结构化解析。

P0 唯一必做 AI 功能：

> **AI JD 结构化解析**

即使 AI API 不可用，用户仍可以手动维护岗位要求，因此不会破坏核心业务。

---

### 8.2 P1：智能增强版

P1 在稳定业务基础上增加三个主要 AI 功能：

1. **AI 学习规划与周复盘**
2. **AI 面试 / 求职复盘**
3. **简历 + JD 匹配分析**

加上 P0 的 AI JD 解析后，共形成 4 个 AI 功能。

---

### 8.3 P2：挑战版

优先级：

**P2-A：RAG 学习资料问答 + 原文引用追溯 —— 必做**

**P2-B：Agent + Tool Calling 求职学习助手 —— 第二优先级**

**P2-C：AI 评估 / A-B 实验 —— 有余力再完成**

可进行的简单 AI 工程评估包括：

- JD 解析 Prompt A/B 对比；
- RAG 不同 `topK` 对比；
- 不同 `chunk size` 对比；
- 不同相似度阈值对比；
- 引用准确性和幻觉情况记录。

整体策略：

```text
P0：先让业务完整跑起来
        ↓
P1：让 AI 自然增强已有业务
        ↓
P2：补 RAG / Agent / Evaluation 技术深度
```

## 十、预计 Controller

Controller 按业务职责划分，第一版预计超过 18 个。

```text
基础档案
- AuthController
- ProfileController
- EducationExperienceController
```

## 十四、风险与降级方案

| 风险 | 处理方案 |
|---|---|
| AI API 不可用或限流 | 保留人工维护岗位要求等传统业务能力，AI 故障不影响核心业务 |
| AI 结果存在错误或幻觉 | AI 只生成候选结果和建议，用户确认后再由 Java Service 校验和保存 |
| AI 分析缺乏依据 | 尽可能展示对应系统数据、JD、面试记录或文档原文，区分“来源事实”和“AI 建议” |
| RAG 开发时间不足 | RAG 位于 P2，不阻塞 P0 / P1 核心交付 |
| Agent 开发复杂度过高 | Agent 为 P2 第二优先级，不影响课程基础 AI 功能 |
| 业务范围过大 | 严格按照 P0 → P1 → P2 开发，优先跑通核心业务闭环 |
| 前端课程要求变化 | 当前按 Vue 3 规划，若任课教师给出新的硬性要求，则以老师最新要求为准 |
| 数据表数量后续调整 | 当前约 28 张候选表，开发前继续 Review，在保持真实业务意义和课程要求的前提下合理合并或拆分 |
